> 此外，如果我们经常处理某些任务且总是遇到困难，为了加快未来的工作效率，请将这些流程保存为一项新技能。

> 切记不要为了更新而更新——只有在理由充分的情况下才动手！

> 如果你做了任何修改，请告诉我。

> 请查看最新的远程 origin/master 或 origin/main 分支。然后，针对过去 24 小时内涉及 &lt;DIRECTORY&gt;（指定目录）的提交，生成一份执行简报 (Exec Briefing)。

> 格式与结构：

> - 使用富文本 Markdown 格式（工作流章节使用 H1 标题，副标题使用斜体，按需使用水平分割线）。

> - 开场白可以写成类似：“以下是 &lt;directory&gt; 过去 24 小时的简报：”

> - 副标题应写为：“负责人叙事性回顾；按工作流分组。”

> - 按工作流 (Workstream) 分组，而不是简单罗列每个提交。工作流的标题应使用 H1。

> - 针对每个工作流写一段简短的叙述性文字，用通俗易懂的语言（plain language）解释变更内容。

> - 为了提高可读性，请使用项目符号（bullet points）和加粗格式。

> - 可以按“人”来列出项目符号，但请加粗他们的名字。

> 内容要求：

> - 在行内包含 PR 链接（例如 [#123](...)），不要使用 “PRs:” 这样的标签前缀。

> - 不要 包含 commit hash（哈希值）或 “Key commits”（关键提交）章节。

> - 同一个工作流下出现多个 PR 是没问题的，但要避免列出“逐个提交 (per-commit)”的清单。

> 范围规则：

> - 仅包含当前工作目录（cwd）或主检出目录（main checkout）内的变更。

> - 仅包含过去 24 小时内的提交。

> - 如果有帮助，可以使用 gh (GitHub CLI) 来获取 PR 的标题和描述。也可以自由获取 PR 的审查意见 (reviews) 和评论。

| 组件 | 描述 | 备注 |

| Skills | 用于复杂任务的专门化智能体能力 |  |

### 什么情况下该封装成插件

- 你想与你的团队或社区共享功能

- 你需要在多个项目中拥有相同的技能和agents

- 你需要版本控制和方便的扩展更新

- 你是在通过市场分销
